## Spark SQL

Spark SQL은 단순한 SQL 문법 기능이 아니라, Spark에서 정형 데이터를 처리하는 엔진이다.
SQL과 DataFrame API 모두 Spark SQL 엔진 위에서 실행된다.

사용자는 DataFrame이나 SQL을 통해 **무엇을 할지(what)** 를 선언하고, 실제로 **어떻게 실행할지(how)** 는 Spark가 결정한다.

- `what` → Logical Plan
- `how` → Physical Plan

DataFrame과 SQL이 선언형 API인 이유도 여기에 있다.

```python
df.filter(...).groupBy(...).count()
```

위 코드는 연산 방법을 직접 지시하는 것이 아니라 원하는 결과를 요청하는 것이다.
반대로 RDD는 사용자가 처리 방법을 더 직접 작성하기 때문에 Catalyst가 개입할 수 있는 범위가 작다.
Python UDF도 Spark가 내부 로직을 볼 수 없기 때문에 최적화가 제한된다.

---

## Catalyst Optimizer

Catalyst Optimizer는 사용자가 작성한 SQL이나 DataFrame 코드를 더 효율적인 실행 계획으로 바꾸는 Spark의 쿼리 최적화기다.

전체 흐름은 다음과 같다.

```text
SQL / DataFrame
      ↓
Unresolved Logical Plan
      ↓
Analyzed Logical Plan
      ↓
Optimized Logical Plan
      ↓
Physical Plan
      ↓
Code Generation
      ↓
실제 실행
```

Spark 버전별 최적화 방식은 다음처럼 발전했다.

```text
Spark 1.x : Rule
Spark 2.x : Rule + Cost
Spark 3.x : Rule + Cost + Runtime
```

---

## Catalyst Optimizer의 처리 단계

### 1. Unresolved Logical Plan

사용자가 작성한 쿼리를 연산자 트리로 만든다.

예를 들어 다음 코드가 있다.

```python
df.filter(col("passenger_count") > 1).select("trip_distance")
```

내부적으로는 다음과 같은 구조가 된다.

```text
Project
  ↓
Filter
  ↓
Relation
```

이 단계에서는 Spark가 아직 `passenger_count`라는 컬럼이 실제로 존재하는지 모른다.

---

### 2. Analyzed Logical Plan

Catalyst가 Catalog를 확인해 쿼리를 검증한다.

- 테이블이 존재하는가?
- 컬럼이 존재하는가?
- 컬럼 타입은 무엇인가?

잘못된 컬럼명을 사용하면 실제 실행 전에 이 단계에서 `AnalysisException`이 발생한다.

분석이 완료되면 컬럼은 다음처럼 Spark 내부의 고유 ID인 `exprId`를 갖는다.

```text
passenger_count → passenger_count#8
trip_distance    → trip_distance#12
```

`#8`, `#12`는 Spark 내부에서 컬럼을 구분하기 위한 고유 식별자다.

---

### 3. Optimized Logical Plan

Catalyst가 여러 최적화 Rule을 적용한다.

대표적인 최적화는 다음과 같다.

#### Constant Folding

실행 전에 계산할 수 있는 상수식은 미리 계산한다.

```text
age > 20 + 10
↓
age > 30
```

행마다 `20 + 10`을 반복 계산하지 않아도 된다.

#### Column Pruning

실제로 사용하는 컬럼만 읽는다.

예를 들어 원본에 여러 컬럼이 있어도 쿼리에서 다음 두 컬럼만 사용한다면,

```text
passenger_count
trip_distance
```

Optimized Plan에서는 필요한 컬럼만 남는다.

```text
Relation [passenger_count, trip_distance]
```

Parquet 같은 컬럼 기반 포맷에서는 필요 없는 컬럼을 디스크에서 읽지 않아도 되므로 효과가 크다.

#### Predicate Pushdown

필터를 가능한 한 데이터 소스 가까이 밀어내려서 읽는 데이터 자체를 줄인다.

```python
passenger_count > 1
```

같은 조건이 Physical Plan의 `FileScan` 안쪽까지 내려가면 다음처럼 보일 수 있다.

```text
PushedFilters: [IsNotNull(passenger_count), GreaterThan(passenger_count,1)]
```

즉, 전체 데이터를 Spark로 읽은 뒤 필터링하는 것이 아니라 가능한 범위에서 먼저 데이터를 걸러서 읽는다.

---

### 4. Physical Plan

Logical Plan의 추상 연산을 실제 Spark 연산자로 바꾼다.

예를 들어 Logical Plan의 `Join`은 단순한 의도이고, Physical Plan에서는 실제 실행 방법이 결정된다.

대표적으로 다음과 같은 Join 전략이 있다.

```text
BroadcastHashJoin
SortMergeJoin
```

한쪽 테이블 크기가 `spark.sql.autoBroadcastJoinThreshold`보다 작으면 BroadcastHashJoin이 선택될 수 있다.
강의 자료에서는 기본값을 10MB로 설명한다.

```text
작은 테이블
    ↓
BroadcastHashJoin

큰 테이블
    ↓
SortMergeJoin
```

SortMergeJoin을 위해서는 양쪽 데이터를 같은 key 기준으로 모으고 정렬해야 하므로 Catalyst가 `Exchange`와 `Sort`를 추가한다.

```text
Exchange = Shuffle
```

즉, 이전에 실행 계획에서 보았던 Shuffle은 사용자가 직접 작성한 것이 아니라 Catalyst가 선택한 Physical Operator를 실행하기 위해 자동으로 만들어진다.

## `.explain(True)` 읽기

다음처럼 실행 계획을 확인할 수 있다.

```python
df = spark.read.parquet("trips")

df.filter(
    col("passenger_count") > 1
).select(
    "trip_distance"
).explain(True)
```

출력은 크게 네 부분으로 나뉜다.

```text
== Parsed Logical Plan ==
== Analyzed Logical Plan ==
== Optimized Logical Plan ==
== Physical Plan ==
```

각 의미는 다음과 같다.

| Plan | 의미 |
|---|---|
| Parsed | 사용자가 작성한 연산 구조 |
| Analyzed | Catalog 및 타입 검증 완료 |
| Optimized | Catalyst Rule 적용 완료 |
| Physical | 실제 실행할 Spark 연산자 |

실행 계획에서 특히 확인할 수 있는 항목은 다음과 같다.

```text
PushedFilters
FileScan
Exchange
Sort
BroadcastHashJoin
SortMergeJoin
```

## 왜 Filter가 두 번 보이는가

Physical Plan에서 같은 필터가 두 번 나타나는 것처럼 보일 수 있다.

```text
Filter passenger_count > 1
    ↓
FileScan
    PushedFilters: GreaterThan(passenger_count,1)
```

하지만 두 연산의 역할은 다르다.

Parquet은 데이터를 Row Group 단위로 저장하며, 각 Row Group에는 컬럼의 min/max 같은 통계가 있다.

예를 들어 조건이 다음과 같다고 하자.

```text
passenger_count > 1
```

Row Group A가 다음과 같다면,

```text
min = 1
max = 1
```

조건을 만족하는 값이 없으므로 Row Group 전체를 읽지 않는다.

반면 Row Group B가 다음과 같다면,

```text
min = 1
max = 4
```

조건을 만족하는 값이 존재할 수 있으므로 Row Group은 읽어야 한다.
하지만 그 안에는 `passenger_count = 1`인 행도 존재할 수 있으므로 Spark의 Filter가 다시 정확한 Row-level filtering을 수행한다.

```text
PushedFilters
= Chunk 단위의 빠르고 거친 필터

Filter
= Row 단위의 정확한 필터
```

따라서 중복 연산이 아니다.

## Cost-Based Optimization (CBO)

Rule 기반 최적화는 실제 데이터 크기를 모른다는 한계가 있다.

예를 들어 Predicate Pushdown은 테이블이 작든 크든 같은 Rule을 적용한다.
하지만 여러 테이블을 Join할 때 어떤 순서로 Join할지는 데이터 크기에 따라 달라질 수 있다.

그래서 Spark 2.2부터 CBO가 추가되었다.

Catalyst는 Catalog에 저장된 통계 정보를 사용한다.

대표적인 통계는 다음과 같다.

```text
row count
table size
distinct values
min
max
null count
```

강의 자료에서는 CBO가 기본적으로 비활성화되어 있다고 설명한다.

```text
spark.sql.cbo.enabled = false
```

### Join Order

여러 테이블을 Join할 때 중간 결과가 가장 작아지는 조합부터 Join하면 다음 단계에서 처리해야 할 데이터가 줄어든다.

관련 설정은 다음과 같다.

```text
spark.sql.cbo.joinReorder.enabled
```

다만 강의에서는 Spark가 모든 Physical Plan을 완전히 비용 계산해 순위를 매기는 방식이라기보다, Rule과 크기 기준으로 연산자를 선택하고 통계는 그 크기 추정을 더 정확하게 만들어 준다고 설명한다.

## Tungsten과 Code Generation

Catalyst가 Physical Plan을 결정하면 Spark의 실행 계층인 Tungsten이 실제 실행 코드를 생성한다.

```text
Physical Plan
    ↓
Java Code
    ↓
RDD 기반 실행
```

`explain()`에서 보는 Physical Plan 자체가 그대로 실행되는 것이 아니라, 최종적으로 생성된 코드가 실행된다.

---

## Whole-Stage Code Generation

Whole-Stage Code Generation은 여러 연산자를 하나의 Java 함수로 합쳐 실행 오버헤드를 줄이는 방식이다.

기존 Volcano Model에서는 각 연산자가 별도의 객체와 `next()` 메서드를 가진다.

```text
Project.next()
    ↓
Filter.next()
    ↓
Scan.next()
```

Row 하나를 처리할 때마다 여러 함수 호출이 발생한다.
또한 연산자 간에 Row를 전달하기 위해 메모리를 거쳐야 한다.

Whole-Stage Code Generation을 적용하면 여러 연산이 하나의 루프로 합쳐진다.

```java
while (rows.hasNext()) {
    row = rows.next();

    if (row.passenger_count <= 1)
        continue;

    output(row.trip_distance);
}
```

즉,

```text
Scan
Filter
Project
```

가 각각 호출되는 것이 아니라 하나의 Java 함수 안에서 처리된다.

이를 통해 다음과 같은 이점이 생긴다.

- 함수 호출 횟수 감소
- CPU instruction 감소
- 데이터 이동 감소
- CPU register 활용 증가
- Query 전용 코드 생성

생성된 코드는 다음으로 확인할 수 있다.

```python
result.explain("codegen")
```

### 주의

Whole-Stage Code Generation에서 말하는 `stage`는 Spark Scheduler의 Stage와 같은 개념이 아니다.

```text
Spark Scheduler Stage
≠
Whole-Stage Codegen Stage
```

## Dynamic Partition Pruning (DPP)

Dynamic Partition Pruning은 작은 Dimension Table의 필터 결과를 이용해 큰 Fact Table에서 필요 없는 Partition을 읽지 않도록 하는 최적화다.

강의에서는 다음과 같이 설명한다.

```text
Dynamic Partition Pruning
= Predicate Pushdown + Broadcast Hash Join
```

관련 설정은 다음과 같다.

```text
spark.sql.optimizer.dynamicPartitionPruning.enabled
```

강의 자료에서는 Spark 3.0부터 기본 활성화라고 설명한다.

### 예시

다음과 같은 테이블이 있다고 하자.

```text
Sales
- 대규모 Fact Table
- sale_date 기준 Partition

Date
- 작은 Dimension Table
```

그리고 Date Table에서 다음 조건으로 필터한다고 하자.

```text
month = 'Jan'
```

DPP는 이 결과를 이용해 Sales Table에서 1월과 관련된 Partition만 읽는다.

```text
Date 필터
    ↓
필요한 날짜 집합 생성
    ↓
Broadcast
    ↓
Sales Scan에 Dynamic Filter 삽입
    ↓
조건과 맞지 않는 Partition Skip
```

전체 Fact Table을 읽지 않기 때문에 스캔해야 하는 데이터 양을 크게 줄일 수 있다.

### 동작 과정

```text
1. 작은 Dimension Table을 Filter
2. 결과로 Hash Table 생성
3. Broadcast Variable 생성
4. Executor에 Broadcast
5. Fact Table Scan에 Dynamic Filter 삽입
6. 조건과 맞지 않는 Partition Skip
7. 실제 읽는 데이터 감소
```

### DPP 제약조건

- Fact Table이 Join Key 기준으로 Partition되어 있어야 한다.
- Equi Join(`=`)이어야 한다.
- 기본적으로 Dimension Table이 Broadcast 가능한 크기여야 한다.
- 큰 Fact Table과 작은 Dimension Table로 구성된 Star Schema에서 특히 효과적이다.

## 전체 정리

이번 수업의 핵심 흐름은 다음과 같다.

```text
SQL / DataFrame
      ↓
Unresolved Logical Plan
      ↓
Analyzed Logical Plan
      ↓
Optimized Logical Plan
      ↓
Physical Plan
      ↓
CBO / Statistics
      ↓
Selected Physical Plan
      ↓
Tungsten
      ↓
Whole-Stage Code Generation
      ↓
Generated Java Code
      ↓
실제 Spark 실행
```

핵심적으로 기억할 내용은 다음과 같다.

1. DataFrame과 SQL은 `what`만 선언하고 `how`는 Catalyst가 결정한다.
2. Catalyst는 Parsed → Analyzed → Optimized Logical Plan → Physical Plan 순으로 실행 계획을 만든다.
3. Column Pruning과 Predicate Pushdown은 읽는 데이터 자체를 줄이는 최적화다.
4. CBO는 통계를 이용해 Join 순서와 크기 추정을 개선한다.
5. Tungsten의 Whole-Stage Code Generation은 여러 연산을 하나의 Java 함수로 합쳐 실행 오버헤드를 줄인다.
6. DPP는 Dimension Table의 필터 결과를 이용해 Fact Table의 불필요한 Partition을 읽지 않는다.
