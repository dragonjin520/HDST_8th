# 우리 따릉이 재배치 시스템에 적용

## 1. 누구의 어떤 문제인가
### 누구의
- 서울시 따릉이 재배치 운영·관리 담당자
- 더 구체적으로는 제한된 배차 인력과 차량으로 여러 대여소를 관리해야 하는 담당자

### 어떤 문제
- 현재 재고만 보고 사후 대응하면, 가까운 미래에 품절 또는 과잉이 발생할 대여소를 미리 알기 어렵다.
- 모든 대여소를 동시에 재배치할 수 없기 때문에 어떤 대여소를 먼저 방문해야 하는지 우선순위를 정하기 어렵다.
- 따라서 현재 재고, 과거 대여·반납 이력, 날씨, 생활인구 등을 이용해 미래 재고를 예측하고 재배치 우선순위를 제공해야 한다.

## 2. 시스템의 Success 정의
성공 시나리오는 가능한 단순하게 정의한다.

### 데이터 수집 성공
- 정해진 수집 주기에 필요한 API 응답을 정상적으로 확보한다.
- 수집한 원본 데이터는 S3 Bronze에 보존한다.
- 정제 가능한 데이터는 Silver 형태로 RDS에 정상 적재한다.
- 동일 데이터를 재수집해도 중복 적재되지 않는다.

### 데이터 처리 성공
- 필수 컬럼이 존재하고 타입 변환이 정상적으로 수행된다.
- 대여소 ID, 시간, 날씨 격자, 생활인구 영역 등 조인에 필요한 Key가 정상적으로 매핑된다.
- 일부 잘못된 레코드가 존재하더라도 사전에 정의한 허용 범위 안이라면 정상 데이터 처리는 계속된다.

### 추론 성공
- 예측 시점에 필요한 최신 Silver 데이터를 읽을 수 있다.
- 모든 대상 대여소에 대해 대여량, 반납량 또는 미래 재고 예측 결과가 생성된다.
- 예측 결과와 모델 버전, 기준 시각, 대상 시각이 Prediction History에 기록된다.
- 서비스에 필요한 최종 결과가 Gold 데이터로 저장된다.

### 서비스 성공
- FastAPI가 Gold 데이터를 정상 조회할 수 있다.
- 사용자가 대여소별 현재 상태, 미래 예상 재고, 부족·과잉 위험, 재배치 우선순위를 확인할 수 있다.
- 최종적으로 담당자가 "어디를 먼저 재배치할 것인가"를 판단할 수 있어야 한다.

## 3. Failure를 단계별로 구체화
Failure를 단순히 작업 실패로 보지 않고 등급을 나눈다.

### Level 1. 경미한 실패 - 계속 진행 가능
- 일부 Optional 컬럼 누락
- 일부 레코드의 비정상 값
- 소수 레코드의 조인 실패
- 일시적인 API 응답 지연

처리:
- 해당 레코드를 제외하거나 기본 처리한다.
- 로그와 데이터 품질 지표에 기록한다.
- 전체 파이프라인은 계속 진행한다.

### Level 2. 부분 실패 - 재시도 또는 부분 재처리
- 특정 페이지 API 호출 실패
- 특정 데이터 소스만 수집 실패
- 일부 Batch의 DB 적재 실패
- 외부 API timeout 또는 일시적인 5xx 오류

처리:
- Exponential Backoff를 적용해 정해진 횟수만큼 재시도한다.
- 그래도 실패하면 실패한 수집 범위나 Batch만 별도로 기록한다.
- 이미 성공한 범위는 다시 처리하지 않고 실패 범위만 재처리할 수 있어야 한다.

### Level 3. 치명적 실패 - 파이프라인 중단
- 필수 스키마가 변경되어 핵심 컬럼이 사라진 경우
- 데이터 수가 예상 범위와 크게 달라 원천 데이터 자체를 신뢰할 수 없는 경우
- Silver 적재 실패로 최신 데이터가 준비되지 않은 경우
- 모델 파일을 읽을 수 없거나 전체 대여소의 추론이 불가능한 경우
- Gold 데이터 생성에 실패하여 잘못된 결과가 사용자에게 제공될 가능성이 있는 경우

처리:
- 해당 Task와 이후 의존 Task를 실패 처리한다.
- 잘못된 데이터를 Gold로 배포하지 않는다.
- 원인과 실패 범위를 로그에 남긴다.
- Bronze 또는 기존 정상 데이터를 이용해 재처리할 수 있도록 한다.

## 4. 성공과 실패를 수치로 Tight하게 정의하기
단순히 "정상적으로 수행"이라고 쓰지 않고 기준을 수치화한다.

예시:
- API 요청 성공률: 99% 이상
- API 실패 시 재시도: 최대 3회
- 필수 컬럼 누락: 1개라도 발생하면 실패
- 중복 데이터: PK 기준 0건
- 조인 실패율: 전체의 1% 이하 허용
- 추론 대상 누락률: 전체 대여소의 0.5% 이하
- Gold 생성 실패: 허용하지 않음
- 예측 결과 생성 시간: 다음 스케줄이 시작되기 전에 완료

※ 실제 임계값은 개발 중 실제 데이터를 확인하면서 iteration을 통해 조정한다.

## 5. Whitelist / Blacklist 방식 적용
### Whitelist
정상이라고 명확하게 정의할 수 있는 항목은 Whitelist 방식으로 관리한다.

예:
- 허용되는 대여소 ID
- 허용되는 성별 코드, 사용자 유형 코드
- 예상되는 API 응답 스키마
- 허용 가능한 날짜 형식

### Blacklist
비정상 패턴을 명확히 알 수 있는 경우 Blacklist 방식으로 관리한다.

예:
- 음수 대여 시간
- 음수 이동 거리
- 존재하지 않는 대여소 ID
- 미래 시각으로 기록된 확정 대여 이력

둘 중 하나만 사용하는 것이 아니라 데이터 특성에 따라 선택한다.

## 7. Raw 품질과 최종 결과 품질을 분리
### Raw / Bronze 데이터 품질
원천 API가 정상적으로 들어왔는지를 확인한다.

- 응답 자체가 존재하는가
- 필요한 필드가 존재하는가
- 데이터 건수가 평소와 크게 다르지 않은가
- API 페이지가 누락되지 않았는가
- 수집 시각과 대상 시각이 올바른가

### Silver 데이터 품질
분석과 모델 입력에 사용할 수 있는지를 확인한다.

- 타입이 정상적으로 변환되었는가
- 중복이 제거되었는가
- 대여소, 날씨 격자, 생활인구 데이터가 정상 조인되는가
- Null 비율이 허용 범위 안인가

### Gold 데이터 품질
최종 사용자가 의사결정에 사용할 수 있는지를 확인한다.

- 모든 주요 대여소에 예측 결과가 존재하는가
- 현재 재고와 예측 결과의 기준 시각이 일치하는가
- 부족·과잉 상태 계산이 정상인가
- 재배치 우선순위가 생성되었는가
- 지나치게 오래된 예측 결과를 서비스하고 있지 않은가

즉 Raw가 정상이어도 Gold가 잘못될 수 있으므로 단계별 품질 기준을 따로 둔다.

## 8. Before -> After로 시스템 효과 정의
### Before
- 담당자는 현재 대여소 재고를 보고 문제가 발생한 뒤 대응한다.
- 가까운 미래의 품절·과잉 대여소를 알기 어렵다.
- 여러 위험 대여소 중 어느 곳을 먼저 방문해야 하는지 판단하기 어렵다.

### After
- 시스템이 대여소별 미래 대여량·반납량과 예상 재고를 계산한다.
- 품절·과잉 위험 대여소를 사전에 표시한다.
- 위험도와 예상 부족·과잉 수량을 기준으로 재배치 우선순위를 제공한다.

### 최종적으로 측정하고 싶은 변화
- 품절 발생 대여소 수 감소
- 품절 지속 시간 감소
- 과잉으로 인해 반납이 어려운 시간 감소
- 위험 대여소 탐지 Recall 향상
- 제한된 재배치 작업으로 해결 가능한 위험 대여소 수 증가

## 9. 각 단계가 잘 작동하는지를 더 구체적으로 보기
단순히 "파이프라인이 성공했다"가 아니라 다음 단계의 결과가 실제로 좋아졌는지를 본다.

```text
API 수집 성공
→ 필요한 데이터가 얼마나 빠짐없이 확보되었는가?

정제 성공
→ 모델에 사용할 수 없는 데이터가 얼마나 줄었는가?

조인 성공
→ 대여소별 Feature Coverage가 얼마나 확보되었는가?

모델 추론 성공
→ 실제값과 비교했을 때 예측 오차가 얼마나 작은가?

Gold 생성 성공
→ 실제 위험 대여소를 얼마나 잘 찾아내는가?

서비스 성공
→ 담당자가 어떤 대여소를 먼저 방문할지 판단할 수 있는가?
```

## 10. 현재 프로젝트에서 우선순위
정해진 시간과 자원 안에서 모든 기능을 동일하게 구현하지 않는다.

### 반드시 완성
1. 안정적인 데이터 수집
2. Bronze / Silver 데이터 관리
3. 데이터 품질 검사
4. 대여소 단위 Feature 생성
5. 수요 또는 미래 재고 예측
6. Gold 데이터 생성
7. FastAPI를 통한 결과 제공
8. Airflow 기반 스케줄링, 재시도, 재처리

### 가능하면 완성
1. Prediction History 기반 운영 모델 평가
2. Spark 기반 대용량 학습 데이터 생성
3. 모델 버전 관리
4. 성능 저하 탐지

### 시간 여유가 있을 때
1. 자동 재학습
2. Champion / Challenger 자동 비교
3. 복잡한 배차 최적화 알고리즘
4. 실시간 Streaming 처리

핵심은 기술을 많이 넣는 것이 아니라, 각 기술이 어떤 요구사항과 실패 시나리오를 해결하기 위해 들어갔는지 근거를 남기는 것이다.

## 11. 최종 발표에서 보여줄 내용 미리 정의
