## Spark Optimization

Spark 최적화는 크게 두 축으로 볼 수 있다.

1. **Compute efficiency**: 각 Task 내부의 계산 효율을 높이는 것
2. **Data movement**: 클러스터 노드 간 데이터 이동, 특히 Shuffle을 줄이는 것

Spark 성능은 단순히 Executor Memory를 크게 잡는 것보다 파일 형식, Partition 수, Shuffle, Cache, Join 전략, 데이터 크기와 메모리 관계를 함께 확인해야 한다.

## RDD와 DataFrame 선택

### 기본 원칙

대부분의 구조화된 데이터 처리에서는 DataFrame이 더 적합하다.

- 고수준 API를 제공해 사용하기 쉽다.
- Catalyst Optimizer와 Tungsten 실행 엔진의 최적화를 받을 수 있다.
- Filter, GroupBy, Join, Aggregation 같은 연산을 Spark가 최적화할 수 있다.

### RDD를 사용하는 경우

RDD는 다음과 같은 상황에서 유용하다.

- 사용자 정의 저수준 연산이 필요한 경우
- 복잡한 처리 과정의 디버깅이 필요한 경우
- Partition과 Memory 사용을 세밀하게 통제해야 하는 경우
- 텍스트 스트림, 바이너리 파일, 사용자 정의 포맷처럼 구조가 정해지지 않은 Raw Data를 처리하는 경우

즉, **일반적인 구조화 데이터 분석은 DataFrame**, **세밀한 제어와 비정형 데이터 처리는 RDD**를 우선 고려한다.

## 효율적인 파일 형식

파일 형식과 압축 방식은 Spark의 I/O 성능에 큰 영향을 준다.

### Columnar Format

Parquet과 ORC는 데이터를 Column 단위로 저장한다.

장점은 다음과 같다.

- **Compression Efficiency**: 같은 타입의 값이 모여 있어 압축 효율이 높다.
- **Column Pruning**: 필요한 Column만 읽을 수 있다.
- **Aggregation Performance**: 특정 Column을 대상으로 한 집계가 빠르다.
- **Predicate Pushdown**: Filter 조건을 Storage Scan 단계에서 미리 적용해 읽는 데이터 양을 줄인다.
- **Schema Evolution**: 기존 데이터에 영향을 최소화하면서 Column을 추가하거나 변경할 수 있다.

### Parquet와 다른 형식

- **Parquet**: Write Once Read Many 방식에 적합하다. 쓰기는 상대적으로 느리지만 필요한 Column만 읽는 분석 작업에서 빠르다.
- **Avro**: 전체 Record를 자주 읽거나 교환하는 Row 기반 처리에 적합하다.
- **CSV / JSON**: 사람이 읽기 쉽고 시스템 간 교환이 편하지만 성능 최적화 목적에는 불리하다.

Spark에서는 일반적으로 `Parquet + Snappy` 또는 `Parquet + LZ4` 조합을 사용하면 읽고 쓰는 데이터 양을 줄일 수 있다.

## Data Warehouse, Data Lake, Data Lakehouse

### Data Warehouse

미리 정의된 Schema에 맞게 정제된 구조화 데이터를 저장한다.

- Schema-on-write
- BI, Reporting, OLAP에 적합
- 데이터 품질과 Governance가 강하다.
- 미리 정하지 않은 형태의 데이터를 수용하기 어렵다.

### Data Lake

정형, 반정형, 비정형 데이터를 원본 형태에 가깝게 저장한다.

- Schema-on-read
- 저장 비용이 비교적 낮다.
- 다양한 분석, 실시간 처리, 머신러닝에 활용할 수 있다.
- 관리가 부족하면 Data Swamp가 될 수 있다.

### Data Lakehouse

Data Lake의 유연성·확장성과 Data Warehouse의 관리 기능을 결합한 구조다.

- Object Storage 위에 구축
- Delta Lake, Apache Iceberg, Apache Hudi 같은 Table Format 사용
- ACID Transaction, Versioning, Lineage 지원
- Data Lake보다 관리 기능이 강하고 Warehouse보다 개방적이다.

비용이 무조건 비싸다기보다는, 저렴한 Object Storage와 필요할 때 사용하는 Compute를 결합해 비용과 성능을 조절하는 구조로 이해하는 것이 적절하다.

## Spark와 JVM

Spark는 주로 Scala로 구현되어 JVM 위에서 실행된다.

PySpark를 사용할 때도 Spark Executor는 JVM에서 실행되며, Python 코드 실행이 필요할 때 별도의 Python Worker Process를 사용한다.

따라서 PySpark에서는 JVM Heap뿐 아니라 Python Process가 사용하는 메모리도 고려해야 한다.

## Spark Memory 구조

Spark는 Memory-only Engine이 아니다.

- 데이터를 Partition 단위로 처리한다.
- 전체 Dataset을 한 번에 RAM에 올릴 필요가 없다.
- 메모리가 부족하면 일부 연산 결과를 Disk로 Spill할 수 있다.
- Cache가 유실되면 Lineage를 이용해 다시 계산할 수 있다.

### On-Heap Memory

Executor Heap은 크게 다음 영역으로 나뉜다.

#### Reserved Memory

- Spark 내부 객체를 위한 예약 영역
- 기본적으로 약 300MB

#### User Memory

- 사용자 정의 데이터 구조
- RDD Dependency 정보
- Spark가 직접 관리하지 않는 객체

#### Unified Memory

`spark.memory.fraction`으로 설정되는 영역이다.

Unified Memory는 다시 다음 두 영역이 공유한다.

- **Execution Memory**: Shuffle, Join, Sort, Aggregation 중간 데이터
- **Storage Memory**: Cache, Persist된 RDD/DataFrame Block

Execution과 Storage는 완전히 고정된 별도 영역이 아니라 상황에 따라 남는 공간을 공유한다.

중요한 우선순위는 다음과 같다.

> Execution Memory는 필요할 때 Storage의 Cache Block을 제거할 수 있지만, Storage는 Execution이 사용하는 공간을 강제로 빼앗을 수 없다.

Storage Block 제거는 LRU 방식으로 처리된다.

### LRU Cache

Least Recently Used Cache 방식이다.

- 가장 오랫동안 사용되지 않은 Cache Block부터 제거한다.
- Cache 또는 Persist를 명시적으로 사용한 데이터에 적용된다.
- 제거된 Block은 Storage Level에 따라 다시 계산하거나 Disk에서 읽는다.

### Executor Memory 5GB 예시

```text
spark.executor.memory = 5GB = 5120MB
memoryOverhead = max(5120MB × 0.1, 384MB) = 512MB
Executor Container Memory = 5120MB + 512MB = 5632MB
```

Heap 내부는 다음과 같이 계산할 수 있다.

```text
Heap                       = 5120MB
Reserved Memory            = 300MB
Usable Heap                = 4820MB
spark.memory.fraction      = 0.6
Unified Memory             = 4820MB × 0.6 = 2892MB
Initial Storage Region     = 2892MB × 0.5 = 1446MB
User Memory                = 4820MB × 0.4 = 1928MB
```

`spark.memory.storageFraction`은 Storage가 다른 Cache Block으로부터 보호받는 초기 영역의 기준이며, Execution과 Storage가 절대적으로 50:50으로 고정된다는 뜻은 아니다.

## Data가 Memory보다 큰 경우

데이터 전체 크기가 Executor Memory보다 크다고 해서 Spark가 처리할 수 없는 것은 아니다.

### 처리 방식

- Spark는 하나의 Task에서 하나의 Partition을 처리한다.
- Source에서 데이터를 Streaming 방식으로 읽는다.
- Cache하지 않는다면 Storage Memory는 입력 전체를 보관하지 않는다.
- 같은 Stage 안의 연산은 Pipeline으로 연결되어 중간 결과를 매번 저장하지 않는다.

Pipeline은 다음 지점에서 끊어진다.

- Shuffle
- Cache / Persist
- Checkpoint
- Sort, Aggregation, Join, Window 같은 Stateful Operation

### Spill

Execution Memory가 부족하면 다음 연산은 중간 데이터를 Local Disk로 Spill한 뒤 나중에 Merge할 수 있다.

- External Sort
- Shuffle Aggregation

반면 Hash 기반 Join은 Build Side Hash Table이 메모리에 들어가야 하므로 일반적으로 Spill에 안전하지 않다.

Spark UI에서는 다음 값을 확인한다.

- Memory Bytes Spilled
- Disk Bytes Spilled
- Peak Execution Memory
- Task Duration

## Shuffle

Shuffle은 동일한 Key를 가진 데이터를 같은 Output Partition으로 보내기 위해 클러스터 전체에서 데이터를 재분배하는 과정이다.

Shuffle은 다음 비용을 발생시킨다.

- 노드 간 Network Transfer
- Disk I/O
- 중간 Shuffle File 생성
- Serialization / Deserialization
- 새로운 Stage 생성

Shuffle은 Wide Dependency를 만들고, 보통 Stage의 경계가 된다.

### Shuffle을 발생시키는 대표 연산

- `groupBy()`
- `groupByKey()`
- `reduceByKey()`
- Key 기반 Aggregation
- Partitioning이 맞지 않는 Join
- `distinct()`
- Global Sort
- Window Function
- `repartition()`
- `repartitionByRange()`

### Shuffle 비용을 키우는 요인

- Data Skew
- 너무 적거나 많은 Shuffle Partition
- 크고 넓은 Row
- 느린 Disk
- 제한된 Network Bandwidth
- 부족한 Execution Memory

### Transformation 최적화

- Global Sort가 필요하지 않다면 `sortWithinPartitions()` 사용
- Range 기반 후속 처리가 필요하면 `repartitionByRange()` 사용
- Filter를 Join, Window, Aggregation보다 먼저 수행
- 필요한 Column만 일찍 `select()`
- 가능한 경우 Spark 내장 Aggregation 함수 사용
- Window Function은 Shuffle과 Sort를 유발할 수 있는 비싼 연산으로 취급

## Caching과 Persist

### Cache가 필요한 경우

Action별 DAG를 비교해 공통으로 반복 계산되는 중간 결과를 찾는다.

다음 조건에서 Cache를 고려한다.

- 같은 Dataset을 두 번 이상 사용
- 여러 Action 또는 Query에서 재사용
- Shuffle, UDF, Window 이후처럼 다시 계산하기 비싼 결과

Cache하기 전에는 먼저 Filter와 Select를 수행해 저장할 데이터 크기를 줄인다.

사용이 끝나면 반드시 해제한다.

```python
df.unpersist()
```

### cache와 persist

`cache()`는 API별 기본 Storage Level을 사용하는 `persist()`의 축약형이다.

- RDD 기본값: `MEMORY_ONLY`
- DataFrame 기본값: `MEMORY_AND_DISK_DESER`

`persist(storageLevel)`을 사용하면 Storage Level을 직접 선택할 수 있다.

### 대표 Storage Level

| Storage Level | 설명 |
|---|---|
| `MEMORY_ONLY` | 메모리에만 저장하며 들어가지 않는 Partition은 필요할 때 재계산 |
| `MEMORY_AND_DISK` | 메모리에 들어가지 않는 Partition은 Disk에 저장 |
| `DISK_ONLY` | Disk에만 저장 |
| `OFF_HEAP` | JVM Heap 바깥에 직렬화해 저장 |
| `*_SER` | 메모리 사용량은 줄지만 직렬화·역직렬화 CPU 비용 증가 |

큰 데이터가 메모리에 전부 들어갈지 확실하지 않다면 `MEMORY_AND_DISK` 계열을 우선 고려한다.

### Cache 주의사항

- 재사용하지 않는 Dataset을 Cache하면 오히려 손해다.
- 너무 큰 Dataset을 Cache하면 Cache Thrashing이 발생할 수 있다.
- Cache Block 하나는 Storage Memory에 온전히 들어가야 한다.
- `MEMORY_ONLY`에서 들어가지 못한 Block은 Cache되지 않고 나중에 재계산된다.
- `MEMORY_AND_DISK`에서는 들어가지 못한 Block을 Disk에 저장한다.

## Checkpoint

Checkpoint는 RDD를 HDFS나 S3 같은 신뢰할 수 있는 Storage에 저장하고 기존 Lineage를 끊는다.

다음 상황에서 사용한다.

- Lineage가 지나치게 길어진 경우
- 중간 계산 비용이 매우 큰 경우
- 장시간 실행되는 Job에서 장애 시 처음부터 다시 계산하기 어려운 경우
- 머신러닝 반복 연산이나 장기간 누적 통계

```scala
sc.setCheckpointDir("/path/to/checkpoint/dir")
processedRdd.checkpoint()
processedRdd.count()
```

Checkpoint도 Lazy하게 동작하므로 Action이 실행되어야 실제로 저장된다.

### Cache vs Checkpoint

| 구분 | Cache / Persist | Checkpoint |
|---|---|---|
| 목적 | 반복 계산 방지 | 긴 Lineage 절단과 안정적인 중간 결과 보존 |
| 저장 위치 | Memory 또는 Local Disk | HDFS, S3 등 신뢰 가능한 Storage |
| Lineage | 유지 | 제거 |
| 유실 시 | Lineage로 재계산 | Checkpoint 파일에서 다시 읽음 |
| 주요 사용 범위 | 같은 Application 내부 재사용 | 장시간 Job, 비싼 중간 결과, 장애 복구 |

Cache와 Checkpoint는 함께 사용할 수 있다.

먼저 Persist한 뒤 Checkpoint하면 Checkpoint 생성 과정에서 동일한 Lineage를 반복 계산하는 비용을 줄일 수 있다.

## Partitioning

Partition 수는 병렬 처리 효율에 직접 영향을 준다.

### Partition이 너무 적은 경우

- 사용 가능한 Core를 충분히 활용하지 못한다.
- Task 하나가 처리해야 하는 데이터가 커진다.
- Task당 Memory 사용량이 증가한다.
- Spill 또는 OOM 위험이 커진다.

### Partition이 너무 많은 경우

- Task Scheduling Overhead 증가
- 작은 Task가 지나치게 많아짐
- 파일 수 증가
- Coordination 비용 증가

최적 Partition 수는 데이터 크기, 연산 종류, Core 수, Executor Memory에 따라 달라진다.

### repartition

```python
df = df.repartition(200)
```

- Partition 수를 늘리거나 줄일 수 있다.
- 전체 데이터를 재분배한다.
- Full Shuffle이 발생한다.
- 데이터 균형을 다시 맞춰야 할 때 사용한다.

### coalesce

```python
df = df.coalesce(20)
```

- 주로 Partition 수를 줄일 때 사용한다.
- Full Shuffle 없이 인접 Partition을 합친다.
- `repartition()`보다 저렴하지만 데이터 불균형이 남을 수 있다.

### Partition이 너무 큰 경우

Partition 하나가 지나치게 크다면 다음 방법을 고려한다.

- `repartition()`으로 Partition 수 증가
- `spark.sql.files.maxPartitionBytes` 조정
- Cache 시 `MEMORY_AND_DISK` 또는 직렬화 Storage Level 사용

강의 자료에서는 Partition당 약 128~256MB를 하나의 참고 범위로 제시하지만, 실제 적정 크기는 연산과 클러스터 환경에 따라 검증해야 한다.

## Data Skew

특정 Key에 데이터가 집중되면 일부 Task만 오래 실행되는 Data Skew가 발생한다.

대응 방법은 다음과 같다.

- 적절한 Partitioning
- Sampling으로 Heavy Key 식별
- Pre-Aggregation 또는 Partial Aggregation
- Heavy Key 분리
- Salting
- AQE의 Skew Join 최적화

### Salting

Skew가 발생한 Key에 임의의 값을 붙여 여러 Key로 분산한 뒤, 1차 집계 후 원래 Key 기준으로 다시 집계하는 방식이다.

예를 들어 `Chicago`에 데이터가 지나치게 많다면 다음처럼 나눌 수 있다.

```text
Chicago → Chicago_1, Chicago_2, Chicago_3
```

## Join 최적화

Join은 Partitioning이 맞지 않으면 Shuffle을 발생시키므로 비싼 연산이다.

### Broadcast Hash Join

큰 Dataset과 작은 Dataset을 Join할 때 작은 Dataset을 각 Executor에 복사한다.

```python
from pyspark.sql.functions import broadcast

result = large_df.join(broadcast(small_df), "id")
```

장점:

- 큰 Dataset을 Shuffle하지 않고 각 Partition에서 Local Join 가능

주의점:

- 작은 Dataset이 모든 Executor Memory에 충분히 들어가야 한다.
- Broadcast 대상이 너무 크면 Executor OOM이 발생할 수 있다.

### Sort-Merge Join

- 큰 Equi-Join에 적합
- 양쪽 데이터를 Shuffle하고 정렬해야 하지만 대용량 처리에 안정적
- Memory가 제한적인 대규모 Join에서 우선 고려

### Shuffled Hash Join

- 각 Shuffle Partition의 Build Side가 메모리에 들어가야 한다.
- 일반적으로 Spill에 안전하지 않으므로 Build Side가 충분히 작을 때만 고려한다.

## Filtering Unused Data

고차원 데이터에서는 필요하지 않은 Row와 Column을 가능한 한 빨리 제거한다.

### Early Filtering

```python
df = df.filter(df["age"] > 21)
```

후속 Join, Aggregation, Window가 처리하는 Row 수를 줄인다.

### Column Pruning

```python
df = df.select("name", "age")
```

불필요한 Column을 제거해 I/O, Memory, Network 비용을 줄인다.

일반적으로 다음 형태를 우선 고려한다.

```python
df = df.filter(df["age"] > 21).select("name", "age")
```

다만 Spark Optimizer가 연산 순서를 바꿀 수 있으므로 실제 실행 계획은 `explain()`으로 확인한다.

## Spark Web UI

Driver는 일반적으로 4040번 Port부터 Live Spark Web UI를 제공한다.

UI에서 확인할 수 있는 주요 항목은 다음과 같다.

### Jobs

- Job별 Duration
- Job에 속한 Stage와 DAG
- Event Timeline
- Executor 추가·제거 시점
- Job 사이 Idle Time

성능을 비교할 때는 입력 데이터, 코드, Spark 설정, 클러스터 자원이 동일해야 한다.

### Stages

Stage 상세 화면에서 Task 분포를 확인한다.

- Task Duration
- Scheduler Delay
- Input / Output Size
- Shuffle Read / Write
- GC Time
- Memory / Disk Spill
- Peak Execution Memory

특정 Task만 오래 걸린다면 Data Skew 또는 Partition 불균형을 의심할 수 있다.

### Storage

명시적으로 Cache 또는 Persist한 RDD/DataFrame의 Block을 확인한다.

- Storage Level
- Cached Partition 수
- Memory 사용량
- Disk 사용량
- Executor별 Block 분포

### Environment

실제 적용된 Spark Property와 Runtime 정보를 확인한다.

코드에 설정했다고 생각한 값이 실제로 적용되었는지 검증할 때 유용하다.

### Executors

Executor별 다음 정보를 확인한다.

- Active / Failed Task
- Completed Task
- Storage Memory
- Peak Memory
- Disk 사용량
- Shuffle Read / Write
- GC Time

### SQL / DataFrame

DataFrame 또는 Dataset API를 사용할 때만 보인다.

- 실행된 Query 목록
- Logical / Physical Plan
- Scan, Filter, Join, Exchange, Aggregate 구조
- 각 Operator의 Metric

RDD API만 사용하면 이 탭이 나타나지 않는다.

## Spark History Server

Spark History Server는 저장된 Event Log를 이용해 종료된 Application의 UI를 재구성한다.

설정 예시는 다음과 같다.

```text
spark.eventLog.enabled=true
spark.eventLog.dir=hdfs://namenode/shared/spark-logs
spark.history.fs.logDirectory=hdfs://namenode/shared/spark-logs
```

History Server와 Spark Application은 같은 Event Log 위치를 사용해야 한다.

```bash
./sbin/start-history-server.sh
```

이를 통해 완료되었거나 중간에 실패한 Application의 Job, Stage, Task, Executor, Storage, SQL Event를 다시 분석할 수 있다.

## 실전 최적화 순서

Spark Job이 느릴 때는 다음 순서로 확인한다.

1. **Spark UI에서 느린 Job과 Stage 식별**
2. **Shuffle Read / Write와 Spill 확인**
3. **특정 Task만 느린지 확인해 Data Skew 점검**
4. **`explain("extended")`로 Join과 Exchange 확인**
5. **불필요한 Row와 Column을 일찍 제거**
6. **Partition 수와 크기 조정**
7. **작은 Table은 Broadcast Join 검토**
8. **반복 사용되는 중간 결과만 Cache**
9. **사용 후 `unpersist()`**
10. **Lineage가 지나치게 길면 Checkpoint 검토**

## 주요 Tuning 설정

### Partition

- `spark.sql.shuffle.partitions`
- `spark.default.parallelism`
- `repartition()`
- `coalesce()`

### Memory

- `spark.executor.memory`
- `spark.executor.memoryOverhead`
- `spark.memory.fraction`
- Off-heap Memory

Off-heap을 사용하면 Executor Container 전체 메모리가 증가하므로 `memoryOverhead`도 함께 늘려야 한다.

### Serialization

- KryoSerializer
- `MEMORY_*_SER` Storage Level

직렬화는 Memory 사용량을 줄일 수 있지만 CPU 비용이 증가한다.

### I/O

- `spark.sql.files.maxPartitionBytes`
- `spark.sql.files.openCostInBytes`

## 피해야 할 실수

- 큰 Dataset에 `collect()` 사용
- 결과 파일 하나를 만들기 위해 무조건 `repartition(1)` 사용
- 재사용 여부를 확인하지 않고 큰 DataFrame Cache
- Broadcast 대상 크기를 확인하지 않고 강제 Broadcast
- Data Skew 무시
- Spark UI의 Spill Metric 무시
- Partition을 무조건 많이 또는 적게 설정
- 설정값만 바꾸고 실행 계획과 Runtime Metric을 확인하지 않는 것

## 핵심 정리

```text
Read     : Spark는 전체 데이터가 아니라 Partition 단위로 읽고 처리한다.
Cache    : Cache Block은 메모리에 온전히 들어가야 하며 LRU 방식으로 제거된다.
Execute  : Sort와 Aggregation은 메모리가 부족하면 Disk로 Spill할 수 있다.
Priority : Execution Memory가 부족하면 Storage Cache를 제거할 수 있다.
Shuffle  : 네트워크와 Disk 비용이 크므로 가능한 한 줄여야 한다.
Verify   : 최적화 여부는 Spark UI와 explain("extended")로 확인한다.
```

Spark 최적화의 핵심은 단순히 메모리를 늘리는 것이 아니라, **읽는 데이터 양을 줄이고, Shuffle을 줄이며, Partition을 균형 있게 만들고, 반복 계산만 선택적으로 Cache하는 것**이다.
