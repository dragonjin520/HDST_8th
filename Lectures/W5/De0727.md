## Why RDD?
Resilient Distributed Dataset

### 하둡/mapreduce의 문제점?
- No data reuse across jobs
- poor support for iterative algorithms

* 더 성능좋거나 쉬운 방법이 있는데 왜 새로운 개념 등장했을까?
    - 그냥 캐쉬 처리하면 안돼? 더 성능 좋은 하드 쓰면 안돼? 그냥 저장하면 되잖아.
        - 근본적인 해결책이 아님.
### immutable RDD
- sync 상관없이 고정됨
- 유지,보수,수정 필요없음
- 문제가 생겼을때 ancester까지 올라가서 다시 연산 수행
    - 단순한 단계 덕분에 쉽게 진행.

- data parallelism


### Action & Transformations
#### Action
    - 값이 떨어지게 나옴. 즉 결과 (cnt, save 등등)
#### Transformations
    - 데이터 전체에 적용되는 연산들 (map, groupby, join 등등)

Action이 오기전까지 Transformations를 적기만 하고 수행하지 않음.
- 코드를 실행하기 전에 여러개의 operation 간에 비교해서 순서바꾸는 등의 튜닝 가능함
    - 예를 들어 새로운 코드가 추가 되었을때 순서를 다시 맞출 수 있음

##### Narrow TF
- 단순한 연산
##### Wide TF
- shuffle이 생기고 여러 분기로 갈라지는 partition
    - 데이터가 움직이므로 막대한 비용 발생
- wide를 줄이고 narrow로 바꿔야함.

### Partition
spark가 정한 task가 돌아가는 최소 단위. 즉 데이터가 쪼개지는 단위
- task는 다 똑같다. data parallel
- partition이 할당되면 Executer가 task(code, config)를 받아서 실행
    - 네트워크에서 독립될 수 있다.
### task
partition에 붙는게 task. 전체 작업이 아님.



### Stage
computation boundaries에 맞춰서 RDD를 잘라 stage로 묶는다.
- shuffle, Action과 같이 비용이 큰 구조로 묶는다.

1. 그다음 스테이지에서 필요한 요구사항 준비
    - stage의 마지막 부분에서 복잡한 계산이 끝난다.
    - stage의 첫 부분에서는 간단한 데이터만 받는다.
2. stage를 최소화하는게 좋다.
    - 복잡한 단계가 줄어드니까

## Why Dag?
### Mapreduce
기본적으로 2단계
- 더 많은 단계를 하고 싶다면 많이 만들어야함. map -> reduce -> map -> reduce
- 실행하는 단계에만 시야가 좁아짐
- 한번에 실행되어서 수정이 어려움.
- 안쓰는 코드도 실행해버림.

### Dag
one job at a time constraint 극복
- 전체적인 job들을 파악 가능
